Notes
This report covers all pages of the filerfd.org public website. Testing was conducted via manual code review, keyboard navigation testing, and automated tooling (axe-core / WAVE). Third-party embeds (Google Maps) are noted where applicable.

Applicable Standards

This report documents conformance with Web Content Accessibility Guidelines (WCAG) 2.1 Level AA, as required by the U.S. Department of Justice final rule under Title II of the Americans with Disabilities Act (ADA) for state and local government entities.

Conformance levels used in this report:

  • Supports — The product meets the criterion without exception.
  • Partially Supports — The product meets the criterion in some but not all cases, or a known limitation exists.
  • Not Applicable — The criterion is not relevant to this product.

WCAG 2.1 — Principle 1: Perceivable

Information and user interface components must be presentable to users in ways they can perceive.

CriterionLevelConformanceRemarks
1.1.1 Non-text ContentA Supports All images have descriptive alt text. Decorative emoji icons are marked aria-hidden="true". The district logo has meaningful alt text.
1.2.1–1.2.5 Time-based MediaA/AA Not Applicable No audio or video content on the site.
1.3.1 Info and RelationshipsA Supports Semantic HTML used throughout. Headings, lists, tables, and form elements are properly structured. Form labels are programmatically associated with inputs.
1.3.2 Meaningful SequenceA Supports Reading and navigation order in the DOM matches the visual order.
1.3.3 Sensory CharacteristicsA Supports Instructions do not rely solely on shape, color, size, or location.
1.3.4 OrientationAA Supports Content is not locked to a single screen orientation.
1.3.5 Identify Input PurposeAA Supports Contact and volunteer form inputs use appropriate autocomplete attributes (name, email, tel).
1.4.1 Use of ColorA Supports Color is not the sole means of conveying information. Active nav links use both color and underline.
1.4.2 Audio ControlA Not Applicable No auto-playing audio.
1.4.3 Contrast (Minimum)AA Supports Primary color palette (navy #1e3a5f on white, white on navy, red #cc2200 on white for large text) meets 4.5:1 for normal text and 3:1 for large text. Gray body text (#334155) on white exceeds 4.5:1.
1.4.4 Resize TextAA Supports Text can be resized up to 200% without loss of content or functionality. Layout uses relative units (rem/%).
1.4.5 Images of TextAA Supports No images of text used. All text is live HTML.
1.4.10 ReflowAA Supports Responsive design adapts to narrow viewports without horizontal scrolling. Wide content (tables) scrolls within its container.
1.4.11 Non-text ContrastAA Supports Form input borders and interactive UI components meet 3:1 contrast ratio against adjacent colors.
1.4.12 Text SpacingAA Supports No CSS overrides that would prevent text spacing adjustments from taking effect.
1.4.13 Content on Hover or FocusAA Supports Dropdown navigation is dismissible, hoverable, and persistent. No tooltip-only content.

WCAG 2.1 — Principle 2: Operable

User interface components and navigation must be operable.

CriterionLevelConformanceRemarks
2.1.1 KeyboardA Supports All interactive elements (nav links, buttons, form fields, FAQ accordion, lightbox, mobile nav) are keyboard accessible. No keyboard traps.
2.1.2 No Keyboard TrapA Supports Lightbox and mobile nav can be dismissed with the Escape key, returning focus to the trigger element.
2.1.4 Character Key ShortcutsA Not Applicable No single-character keyboard shortcuts implemented.
2.2.1–2.2.2 TimingA Not Applicable No time limits on any content or interaction.
2.3.1 Three FlashesA Not Applicable No flashing content.
2.4.1 Bypass BlocksA Partially Supports Navigation is consistent across pages. A skip-to-main-content link has not been implemented but is a planned improvement.
2.4.2 Page TitledA Supports Every page has a unique, descriptive <title> including the page name and district name.
2.4.3 Focus OrderA Supports Focus order follows a logical top-to-bottom, left-to-right sequence matching visual layout. Mobile nav and lightbox manage focus programmatically on open/close.
2.4.4 Link Purpose (In Context)A Supports Link text is descriptive. Icon-only links (Facebook) have aria-label attributes. "Read More" style links are not used.
2.4.5 Multiple WaysAA Supports Site navigation and footer links provide multiple ways to reach each page.
2.4.6 Headings and LabelsAA Supports Headings are descriptive and consistent. Form labels accurately describe their fields.
2.4.7 Focus VisibleAA Supports Browser default focus indicators are preserved. Interactive elements show visible focus outlines on keyboard navigation.
2.5.1–2.5.4 Pointer/Motion GesturesA/AA Not Applicable No multipoint gestures or motion-activated functionality.

WCAG 2.1 — Principle 3: Understandable

Information and the operation of the user interface must be understandable.

CriterionLevelConformanceRemarks
3.1.1 Language of PageA Supports All pages declare lang="en" on the <html> element.
3.1.2 Language of PartsAA Not Applicable No content in languages other than English.
3.2.1–3.2.2 On Focus / On InputA Supports No unexpected context changes occur on focus or input. Form submission requires explicit button activation.
3.2.3 Consistent NavigationAA Supports Header navigation and footer are identical across all pages, loaded from a shared component.
3.2.4 Consistent IdentificationAA Supports Components with the same function are identified consistently across pages.
3.3.1 Error IdentificationA Supports Required form fields are marked with required and aria-required="true". Browser-native validation identifies errors.
3.3.2 Labels or InstructionsA Supports All form fields have visible labels. Required fields are indicated both visually and programmatically.
3.3.3 Error SuggestionAA Supports Browser-native validation provides error suggestions for incorrectly completed fields (e.g. invalid email format).
3.3.4 Error PreventionAA Supports Contact and volunteer forms require confirmation via submit button. No irreversible transactions on the site.

WCAG 2.1 — Principle 4: Robust

Content must be robust enough to be interpreted by a wide variety of user agents, including assistive technologies.

CriterionLevelConformanceRemarks
4.1.1 ParsingA Supports HTML is well-formed with no duplicate IDs or improperly nested elements.
4.1.2 Name, Role, ValueA Supports All interactive elements use native HTML elements with appropriate roles. Custom components (mobile nav, FAQ accordion, lightbox) use ARIA attributes (aria-expanded, aria-modal, role="dialog") to communicate state.
4.1.3 Status MessagesAA Supports Form submission success messages use role="alert" and aria-live="polite" so screen readers announce them without requiring focus.

Known Limitations

  • 2.4.1 Bypass Blocks — A skip-to-main-content link is not currently present. This is a planned improvement.
  • Third-party embeds — The Google Maps embed on the Contact page is provided by Google and may have accessibility limitations outside the district's control. The iframe has a descriptive title attribute to provide context to screen reader users.
  • PDFs — Any PDF documents linked from the site (meeting agendas, budget documents) should be accessible. The district is advised to ensure documents are properly tagged before posting.

Testing Methodology

  • Manual code review of all HTML pages against WCAG 2.1 AA success criteria
  • Keyboard navigation testing across all interactive elements and pages
  • Automated testing using WAVE (WebAIM) and axe-core
  • Visual review across desktop and mobile viewports
  • Screen reader spot-check using macOS VoiceOver
